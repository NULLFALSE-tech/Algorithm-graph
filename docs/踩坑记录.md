# 踩坑记录

> 谁踩到谁记，一条一行。**记这个的唯一目的：让后面的人少花时间。**
> 先遣员（P4 张超明）第一个走完全流程，这里前 5 条都是他记的。

## 格式

| 现象（你看到什么） | 原因 | 怎么解决 | 花了多久 |
|---|---|---|---|

现象要写**你能截图的那句话**，比如 `Permission denied (publickey)`，不要写「推不上去」。

## 值得单独记一笔的（新人最容易卡 20 分钟以上的）

- **`git clone` 卡住不动**：多半是网络。换手机热点试一次，能通就是网络问题，不是你操作错。
- **`Accept invitation` 点了没反应**：先确认登录的是**你自己的账号**（右上角头像），不是组长的。
- **`git push` 之后网页上看不到你的分支**：检查推的是不是 `feat/xxx` 而不是 `main`；分支会出现在仓库页的 Branch 下拉里。
- **在 GitHub 建仓库时勾了 `Add a README`**：远程会多一个 `Initial commit`，和你本地的根提交**没有共同祖先**，
  于是 `git push` 被拒（`non-fast-forward`）。要么建仓时什么都别勾，要么 `git pull --allow-unrelated-histories`。

## 六、第 6 条：那次合并冲突是怎么解决的（P1 补记）

| 现象 | 原因 | 怎么解决 |
|---|---|---|
| 合并 `docs/req-02` 时 Git 报 `CONFLICT (content): Merge conflict in docs/Project_Requirements_and_Design.md` | P2 与 P3 从同一基线分头开工，**都要在目录表的相邻两行各加自己那一行**，改动落在同一个 diff 块里 | 见下 |

冲突现场：

```
<<<<<<< HEAD
| 一、背景与目标 | P2 王瑞 | 已完成 |
=======
| 二、功能与数据 | P3 郭子琪 | 已完成 |
>>>>>>> docs/req-02
```

**判断过程**（不是无脑选一侧）：

1. 先看两边改的是不是同一个单元格——**不是**。P2 加的是「一、背景与目标」那一行，P3 加的是「二、功能与数据」那一行。
2. 再看有没有语义冲突——**没有**。两章的正文各自写在自己那一节里，互不引用。
3. 结论：**两行都保留**，顺序按章节号排（一在前、二在后），删掉 `<<<<<<<`、`=======`、`>>>>>>>` 三行标记。

解决后的结果：

```
| 一、背景与目标 | P2 王瑞 | 已完成 |
| 二、功能与数据 | P3 郭子琪 | 已完成 |
```

**事后反思**：这次冲突的根因不是「两人手贱」，而是**目录表本身是共享资源**。
如果一开始就把目录表交给 P1 统一维护、组员只写自己那一节，就不会冲突。
但课程要求「真实体验冲突解决」，所以这次刻意保留了这个共享点，并在 README 6.1 里写清了判断过程。

**顺带一条硬教训**：`data/algos.json` 是「一条算法一行」，好处是 diff 干净、冲突范围永远可控，
坏处是**同一行改两个字段就必然冲突**。六人并行时必须先约定「谁改哪个字段」。

## 七、第 7 条：`--export` 把样式表一起删了（P4 复核时发现）

| 现象 | 原因 | 怎么解决 |
|---|---|---|
| 跑完 `python app.py --export web` 后，首页变成纯文本、`web/style.css` 不见了 | 导出函数第一步是 `shutil.rmtree(输出目录)`，而我把输出目录写成了 `web`——它既是源目录又是目标目录，于是先把自己删了 | 导出目录改成独立的 `_site`；并在函数开头加一句断言：输出目录不得是 `web`、`data` 或项目根 |

**教训**：凡是带 `rmtree` 的函数，参数必须由「白名单 + 断言」两道关，不能由调用者随便传。
这条和 `git reset --hard` 是同一类错误：**破坏性操作的参数默认值要选最安全的那个**。
