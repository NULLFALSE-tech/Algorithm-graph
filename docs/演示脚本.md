## 口播全文

[0:00]
老师好，我们是 13 班 3 组，这次作业的题目是 C 语言算法知识图谱。选这个题，是因为课本里的数据结构本来就互相依赖，用一张图来讲，比用目录来讲清楚得多。接下来六分半，我一边操作一边说明。这段视频不留剪辑，屏幕上看得到的地方我都会指到。

[0:30]
先说需求文档，全篇分六块，背景目标，知识原理，主要功能，可视化设计，技术方案，团队分工。这六块不是凑数的标题，每块都对应仓库里的具体文件和具体负责人，谁写哪一块，文档里写着名字。文档就放在仓库里，随时能点开看，不是交上去就没人翻的附件。

[1:00]
这是首页，也是整张图谱的全貌。76 条算法，按 13 章归位，分 5 层摆放，32 条依赖边把它们连成一张网。鼠标停在节点上，和它相连的依赖边会亮起来，谁依赖它、它又依赖谁，一眼就分得清，点一下进详情页。整张图一屏放得下，不用缩放也不用拖。

页面顶部是检索框。输入 二分 回车，命中的节点变亮，没命中的淡下去，视线自然落到结果上。再输一个库里没有的词，比如 红黑树排序，整张图变灰，提示命中 0 份，它不会为了画面好看硬塞一个结果。检索是服务端做完再吐页面的，敲回车就出结果。

切到 /all，这里是全量列表。顶上先给一句计数，共 76 条、当前显示多少条。下面按 13 章分组，每章带一句定位。每张卡片写清算法名、源文件名和行数、一句简介，再挂标签说明是精讲还是导读、能不能单独编译。列表和图读的是同一份数据，不会出现两个说法。

最后进一个详情页。往下依次是官方原版图解、真实 C 代码、精讲、实跑输出、在本机跑一遍。代码逐字取自仓库没有改写，带行号，关键字有颜色；33 条精讲写在代码旁边，用一张表说清每个阶段代码在做什么、变量和内存怎么变；87 张图解全部挂在页面里；实跑输出是 gcc 编译后真实抓下来的 stdout，不是手写的；最后一段告诉你这个文件想在自己电脑上跑该敲哪两条命令。地址是固定的，复制链接发到群里，别人打开就是同一页。

[3:00]
技术方案先说一条底线，这套东西断网也得能演示。后端只用 Python 标准库里的 http.server，一个框架都没有，交上去不用装任何依赖。前端是纯 HTML，CSS，JavaScript，一个 CDN 都不引，所以拔掉网线，按 Ctrl+R 刷新，页面照常打开。

数据只有一个入口，data 目录下的 json 文件。页面里不写死任何一条算法，改 json 就等于改页面内容，加一条新算法只需要动一份数据。全站源码 7174 行，这个数字是脚本数出来的，不是拍脑袋估的。

为什么不上框架。因为要交的是在别人电脑上能跑的东西，不是只能在我电脑上跑的东西。老师打开仓库根目录，敲一句 python app.py，浏览器打开就能看，不用 pip 装任何东西，演示现场也不会卡在配置上。这一句命令端口写在里面，不熟悉命令行的人照着念也能跑起来。

json 的字段做了统一命名，前端读的时候不用为每个文件写一套解析，加一种新内容也不用改页面。

[4:30]
协作部分。两个阶段开了 14 条分支，提了 4 个 PR，一人一条线。每条分支只动自己负责的文件，改完提 PR，等审，等合并，主分支始终能跑。PR 里写清改了什么、为什么改，审的人不用逐行翻代码也能判断。合并完分支就删，所以 Branches 页只剩 main，每一条的名字、PR 号和合并提交都留在 README 第六节的两张表里。

中间撞了一次真实冲突。两个人都在需求文档的同一张目录表里，各加自己那一行，还加在了相邻位置，Git 把两边并排摆出来。我们坐下来一条一条对，发现不是抢同一个格子，是抢相邻两行，那就两行都留，顺序按章节号排。判断过程完整写进了踩坑记录第 6 条，README 第 6.1 节也留了同一份，没有藏着。

[5:30]
最后说 Vibe Coding。这次分工很清楚，AI 负责快，人负责对。骨架、样板代码、重复的样式，交给它，省下来的时间用来想结构，想交互，想数据怎么组织，这部分它替不了人。

它也错过。搜索高亮那段是它给的，它把用户输进来的词原样拼进 HTML，页面看着完全正常，但别人只要在搜索框里写一段脚本，这段脚本就能在别人的浏览器里跑起来。人逐行看代码才发现，改成先转义再输出。这次连原始提示词一起记进了 AI 使用记录。它擅长写看起来对的代码，不擅长判断这些代码安不安全。所以我们的规矩是，AI 产出的东西必须能验证，验证不了的部分不写进结论。

片子到这里，谢谢老师。
