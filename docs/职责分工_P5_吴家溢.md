## 二、任务 B：提交规范巡检（`docs/提交规范巡检_2026-11-26.md`）

这一步是「**拿数据说话**」，不是写感想。每一条都要有命令输出支撑。

### B1. 跑这五条命令，把输出原样贴进报告

```bash
cd /d/CODE/Algorithm-graph

# ① 每人提交了多少次
git shortlog -sn --all

# ② 提交时间分布（看是不是全挤在一天/一分钟）
git log --pretty=format:'%ad' --date=format:'%Y-%m-%d %H:%M' | sort | uniq -c

# ③ 最近 40 条提交说明（看格式）
git log --pretty=format:'%h %an %ad %s' --date=short -40

# ④ 分支有多少条
git branch -a

# ⑤ 合并节点（有几个是解决冲突产生的）
git log --merges --oneline
```

> 这五条都是**只读**命令，不会改任何东西。放心跑。

### B2. 按这张表逐项判 ✅ / ⚠️ / ❌

| 检查项 | 合格标准 | 怎么判 |
|---|---|---|
| 提交说明格式 | 形如 `类型(范围): 一句话`；**纯文档类可省范围，写成 `docs: 一句话`**。不许出现「update」「修改」「1」这种裸词 | 看 ③ 的输出 |
| 作者名 | 是中文真名（邓宇轩/王瑞/郭子琪/张超明/吴家溢/焦明远） | 看 ① ③ |
| 提交时间 | **至少跨 5 个不同日期**，不是同一天堆完 | 看 ② |
| 作者分布 | 6 个人都有提交，组长不超总量的 60% | 看 ① |
| 分支隔离 | 有 ≥ 5 条 `docs/xxx` `feat/xxx` 分支 | 看 ④ |
| 冲突记录 | 至少有 1 个 merge commit 是手工解冲突产生的 | 看 ⑤ + PR 描述 |
| 禁止项 | 无 `--force` 强推、无 `reset --hard` 抹历史 | 看 ⑤ 是否出现历史断裂 |

> 📌 **先给你打个预防针：现在跑，有两项大概率是 ❌，这是真实现状，不是你的错**：
> - **提交时间**：全仓 35 个提交只落在 **4 个不同分钟**里（其中 31 个挤在同一分钟），所以「跨 5 个日期」现在肯定不达标；
> - **作者分布**：组长 30 个、其余 5 人合计 5 个，组长占比约 86%，超过 60% 的上限。
>
> **你的任务是如实记录，不是改数字、也不是改历史去凑。**
> 这两项会在 P2–P6 各自提交之后自然改善（每人 3 次、分几天推），到 11/26 再跑一次就能看到变化。
> 报告里这样写就行：「当前 ❌，原因是 X，随 11/19–11/26 的提交预期改善」，比硬凑成 ✅ 强得多。

### B3. 发现问题怎么办

**只写进报告，标出来，交给组长。⛔ 自己绝对不要动 Git 历史。**

改历史（rebase / reset / force push）比重写还危险：一次操作能把全组仓库搞坏，而且不可恢复。
